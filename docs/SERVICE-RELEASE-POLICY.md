## 앱 안정성과 유지보수를 기준으로 배포·릴리즈

- 커밋·push·main 통합은 검증된 작업 단위로, 정식 릴리즈는 사용자가 설치할 이유가 있는 변경 단위로 진행한다. main 통합, 프리뷰 게시, 정식 릴리즈, 사용자 환경 적용, 판매 개시는 별도로 기록한다. 날짜·작업 완료·태그 생성만으로 다음 단계를 자동 합격 처리하지 않는다.
- 일반 릴리즈 대상은 사용자에게 보이는 기능·체감 품질 개선·중요 오류 수정이다. 문서·테스트·내부 리팩터링만으로는 보통 새 패키지를 배포하지 않는다. 긴급 보안·데이터 손실·실행 불가 수정은 필요한 검증 후 바로 배포한다. 정기 일정은 점검 계기이며 릴리즈 의무가 아니다.
- 정식 릴리즈는 다음을 모두 충족한다: 최신 통합 SHA의 프로젝트 필수 검사 통과, 변경 관련 실제 실행/회귀 검증 통과, 알려진 출시 차단 결함 0건, 배포 패키지의 설치·업데이트·시작·종료·재시작 검증, 데이터 보존과 복귀 절차 확인, 버전·코드·파일의 일치, 유지보수에 필요한 진단·문서·담당/후속 조치 확보.
- 출시 차단 결함은 실행 불가·크래시·영구 멈춤·핵심 기능 중단, 데이터 손실/임의 초기화, 인증 우회/비밀 노출/원치 않는 전송, 장치·백그라운드 작업 중지 불능, 재시도 폭주/무제한 자원 증가, 업데이트 실패로 복구할 수 없는 상태, 이전 안정판 대비 중대한 회귀다. 핵심 경로의 검증 누락도 보류다. 경미한 문제는 영향·우회 방법·후속 조치를 기록하고 진행할 수 있다.
- 새로 바뀐 기능이 의도대로 동작하는지는 확인하되, 재미·몰입·말투·추천/생성 콘텐츠의 우수성·콘텐츠 수를 전역 출시 필수 조건으로 만들지 않는다. 콘텐츠 개선 목표와 앱의 배포 안정성 판정을 구분한다. 콘텐츠 평가 지표 미달만으로 안정성 수정 배포를 막지 않는다. 콘텐츠를 통해 발생한 보안·데이터 손상·실행 결함은 여전히 차단 대상이다.
- 유지보수 검토는 변경 범위에 맞춘다: 재현 절차와 원인/수정 설명, 필요한 회귀 검사, 설정·저장 형식 호환성, 새 의존성/런타임의 필요성·버전 고정·갱신/보안 위험·배포 고지, 비밀 없는 오류/로그 진단, 변경된 사용/운영 문서와 복귀 방법을 확인한다. 모든 기술 부채 제거·전체 구조 재설계·임의의 커버리지 목표를 출시 의무로 추가하지 않는다.
- 매 릴리즈에는 실제 배포본의 기본 실행과 업데이트/데이터 보존을 확인한다. 장시간 시험·기기 조합·전체 설치 행렬은 최초 배포 또는 캡처/저장/설치/런타임 등 영향이 큰 변경에서 넓히며 작은 수정마다 무관한 전체 시험을 반복하지 않는다. 유효한 이전 증거는 코드·의존성·환경의 영향 분석과 함께 재사용할 수 있다. 빌드·mock 통과는 필요한 실제 실행 검증을 대신하지 않는다.
- 프리뷰는 제한·미검증 범위를 표시하고 실험 기능을 격리한다. 데이터 손실·보안·중지 불능 등 사용자 보호 결함을 프리뷰라는 이유로 허용하지 않는다. 선택 기능만 막힌 경우 기본 비활성 경로와 격리를 검증하면 제외하고 나머지를 배포할 수 있다. 핵심 기능이 막히면 정식 릴리즈를 보류한다.
- 출시 기록에는 변경 이유, 대상 SHA·버전·패키지 해시, 검증 결과/환경/원본 경로, 알려진 문제, 복귀 방법, 게시/설치 결과를 남긴다. 실패·미검증을 숨기지 않고 시간 경과·사용자 무응답·종료 코드만으로 합격을 만들지 않는다. 개인정보·인증 원문은 게시하지 않는다.
- 게시된 태그·파일은 덮어쓰지 않는다. 원격 태그/첨부 파일/해시를 확인하고, 사용자 적용은 백업·데이터 호환성·대상 앱 소유권/사용 상태 확인 후 정상 종료·전환·재실행으로 검증한다. 실패하면 배포 확대를 멈추고 검증된 복귀 또는 수정 버전을 제공한다.
- 조건을 충족하면 기존 권한 범위에서 별도 승인 대기 없이 통합·릴리즈·적용한다. 판매 개시·가격·공개 범위 확대·새 개인정보 수집 등 기존 권한 밖의 결정은 필요한 준비를 마친 뒤 사용자에게 확인한다. 판매/유통의 별도 요구사항은 일반 유지보수 릴리즈와 구분한다.
- 이 원칙을 프로젝트의 실제 배포 방식에 맞춰 적용한다. `docs/SERVICE-RELEASE-POLICY.md`에 프로젝트별 실행/검증 방법을 기록하며, 특정 앱의 콘텐츠·모델·응답 시간·표본 수를 다른 프로젝트에 강제하지 않는다. 정책 수정만으로 제품 버전을 올리거나 출시 합격을 선언하지 않는다.

## 정식 릴리즈 필수 항목

1. **릴리즈할 이유:** 기능·품질·중요 오류 개선을 릴리즈 노트로 설명할 수 있다. 무관한 미완성 작업을 끼워 넣지 않는다.
2. **검증된 통합 코드:** 격리 worktree에서 npm ci, 최신 통합 SHA의 npm run check, 영향 영역의 실제 실행/회귀 검증을 통과한다. 인증 변경은 node scripts/verify-account-device.mjs 및 Electron의 scripts/verify-account-runtime.cjs를 추가한다. 실제 계정 확인은 --existing-account와 별도 프로필을 사용하며 자격 증명을 직접 읽지 않는다.
3. **기본 실행 안정성:** 실제 패키지로 시작→설정→해당 기능 사용→중지→종료→재시작이 정상이다. 창/서버/워커의 크래시·멈춤·고아 프로세스가 없다. 캡처·마이크·녹화 변경은 실제 장치의 연결/해제와 늦은 결과 취소를 확인한다. 방송 밖 활동은 일반 방송 중지와 구분하되 앱 전체 종료 시 소유한 작업은 종료돼야 한다.
4. **데이터와 실패 복구:** 업데이트 뒤 기존 설정·기록·저장 위치를 유지한다. 저장 실패·외부 서비스 오류·장치 단절 등 영향 있는 실패에서 오류가 설명되고 정상 복구/재시도가 가능하다. 무한 재시도·조용한 초기화·자원 누수가 없다. 저장 형식 변경은 백업 데이터 복사본으로 마이그레이션과 구버전 복귀 호환성을 검증한다.
5. **배포본 검증:** 코드 SHA·앱 버전·패키지 해시가 일치한다. 실제 새 설치와 이전 배포본 업데이트 후 실행을 확인한다. 최초 배포 및 설치기/런타임/의존성 변경은 개발 환경 없는 지원 Windows에서 검증한다. 작은 수정은 영향 분석에 따라 유효한 환경 증거를 재사용하되 새 패키지의 기본 실행과 업데이트 확인은 수행한다.
6. **유지보수 가능성:** 변경 이유·재현/검증 절차·관련 문서를 남긴다. 새 설정/의존성의 필요성과 호환성을 검토한다. 오류 발생 시 버전·상태·안전한 로그로 진단할 수 있어야 하며 알려진 문제에는 우회 방법과 후속 작업을 연결한다. 실행 중 요청/장시간 미디어/저장 구조를 바꾼 경우 지속 사용 시 메모리·CPU·디스크·큐가 비정상적으로 증가하지 않는지 확인한다. 시험 시간과 부하는 해당 위험에 맞춰 사전에 정하고 기록한다.
7. **게시와 복귀:** 새 버전·릴리즈 노트·이전 버전 복귀 방법을 준비한다. 원격 파일을 확인한 후 STABLE-INSTALLATION.md의 고정 설치 절차로 백업·해시 대조·진입점 전환·실제 실행을 검증한다. 실행 중 사용자 앱을 강제 교체하지 않는다. 복귀 시 새 기록을 무조건 과거 백업으로 덮어쓰지 않는다.

개별 조건은 PASS/FAIL/NOT_TESTED/N/A와 근거를 기록한다. N/A는 영향 없는 영역이나 미제공·격리된 선택 기능에만 허용한다. 필수 항목의 실패·미검증은 보류하며 전체 콘텐츠 개선 로드맵의 완료를 기다리지는 않는다.

## 기존 문서와의 관계

이 문서가 일반 배포·정식 유지보수 릴리즈의 기준이다. FEATURE-PROMOTION.md의 능동적 편입/진행은 이 기준 안에서 수행한다. RELEASE-GATES.md의 콘텐츠·몰입·대화 품질 목표는 제품 개선/판매 준비 참고로 남기며 일반 릴리즈의 일괄 차단 조건으로 사용하지 않는다. INSTALLER.md와 RELEASE-GATES.md의 실제 설치·production·보안·배포 복구 차단 조건은 해당 배포 경로에서 계속 준수한다. 판매 개시 및 유통 채널 요구사항을 충족했다는 뜻은 아니다.

이전 초안의 발언 50개, 응답 8/15초, 적절성 90%, 기억 20개 시나리오, 게임 2종/정해진 2시간 시험, FPS 비율 등 일괄 합격선은 폐기한다. 이러한 지표를 별도 개선 실험에서 사용할 수는 있지만 앱 안정성 릴리즈에 자동으로 강제하지 않는다.

## 전역 적용·검증 기록

같은 `SERVICE-RELEASE-POLICY` 블록을 교체하므로 구 정책과 중복 적용하지 않는다. 설치 명령은 `node scripts/install-release-policy.mjs --target <기존 전역 지침 절대 경로>`이며 Windows/WSL Codex AGENTS.md와 Claude CLAUDE.md 네 곳에 적용한다. 블록 외 지침은 보존하고 변경 전 사본·해시는 작업 worktree의 artifacts/release-policy-*에 보존한다. 재적용 시 changed=false를 확인한다. 기존 실행 작업은 재개 시 수정 지침을 다시 읽어야 한다.

작업: codex/service-release-policy, ../00_game_backseat-worktrees/service-release-policy. 이전 콘텐츠 기준은 main에 통합되지 않은 4702df2에만 있었고 사용자 정정에 따라 이 문서로 대체했다. 최신 기준 main은 a0ddd63abe26c2a058036171010960af2fd750a6. 구 설치/검증 원본은 artifacts에 이력으로만 보존하며 현행 정책 또는 새 제품 검증으로 재사용하지 않는다. 이번 작업은 정책/설치기/문서 연결만 변경하며 제품 릴리즈나 실사용 수용 시험을 실행하지 않는다.

수정본 검증: npm run check의 647개 테스트와 TypeScript/Vite 빌드 통과(artifacts/policy-stability-check.log). Windows/WSL 네 파일 설치 후 재적용 모두 changed=false(artifacts/policy-stability-install.json, policy-stability-reapply.json). 변경 전 사본과 원문 대조로 정책 블록 외 지침이 그대로임을 확인했다. 백업 원본은 artifacts/release-policy-c9a8dbea-4b70-466d-af3b-c763c18d1f29에 보존하며 원격에 게시하지 않는다.

최종 통합 검증: 원본 작업 SHA 96a2ba8e361c6cc3512035b79d96fcd32f580e32를 최신 main a0ddd63에 격리 squash 통합했다. npm run check의 647개 테스트와 빌드가 통과했다(../service-release-policy-integration/artifacts/policy-stability-integration-check.log). 통합 커밋은 Git 이력의 원본 SHA로 추적한다. 변경 파일은 지침·정책·설치기 5개이며 제품 코드/버전/사용자 앱은 변경하지 않았다. 원본 정책 백업과 검사 증거가 있는 두 작업 공간은 detached 상태로 보존하고 통합된 작업 브랜치만 정리한다.
