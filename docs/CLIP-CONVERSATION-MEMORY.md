# 클립에서 읽은 대화가 다음 방송으로 이어지는 기억

2026-09-13. 기준 `a3c2d26d4fe89911d39742a4f5b49b9af72a45b1`, 브랜치 `codex/clip-conversation-memory`. 개발·합성 프로필·검사·로그는 `G:/dev/ai/00_game_backseat-worktrees/clip-conversation-memory`에 분리했다. 사용자 앱과 기존 수집기, 화면·마이크·출력 장치는 조작하지 않았다.

## 발견과 변경

주 방향은 스트리머와 관객의 사실적인 소통이다. [회상 말투 개선](RECALL-SPEAKING-STANCE.md) 이후, 방송 밖 클립에서 나눈 대화가 다음 방송으로 이어지는지 확인했다. 기존에는 댓글이 `member.memories`에 남아도 라이브 컨텍스트가 저널이 있으면 그 배열을 제외해 기억이 전달되지 않았다. 수정 전 실제 코드의 합성 재현은 `artifacts/clip-memory-before.json`에 있다. 댓글 두 개가 저장됐지만 라이브의 recollections는 비었고 별도 클립 기억 경로도 없었다.

이번 구현은 **클립에 남은 텍스트를 읽은 경험**을 다룬다. 원본 영상·음성을 재생하거나 모델이 클립의 녹화 내용을 분석하는 기능을 추가한 것은 아니다. [공개 한국 방송 채팅 조사](CHAT-ATTENTION-DONATIONS.md)의 실제 표본과 이번 합성 검사를 구분한다. 외부 채팅 원문·실사용 대화는 모델 검사에 넣지 않았다.

- 댓글을 만들 때 관객에게 전달한 제목·게임·장면 요약·채팅·최근 비삭제 댓글을 스냅샷으로 잡는다. 오래된 대댓글 대상과 조상은 최근 30개 밖에 있어도 최대 4단계까지 함께 전달한다. 미디어 플래그를 재생 증거로 삼지 않는다.
- 성공적으로 게시한 관객별로 읽은 원문 ID와 공개 내용의 SHA-256, 읽은 시각을 clips 저장소에 남긴다. 댓글과 읽기 기록은 같은 `Clips.change` 및 JsonStore 저장으로 커밋된다. 응답이 실패·취소·차단되면 읽은 것으로 승격하지 않는다. 같은 모델 묶음에서 다른 관객이 새로 쓴 답은 아직 읽은 댓글로 넣지 않는다.
- 모델 응답 대기 중 읽던 원문이나 제목·설명이 바뀌면 응답을 저장하지 않는다. 새로 추가된 댓글은 기존 입력 스냅샷에 없으므로 읽은 것으로 처리하지 않는다. 삭제·내용 변경·미래 시각의 기록은 회상 후보에서 제외한다. 제목·설명 버전이 바뀌면 기존 내용을 새 설명에 붙여 기억하지 않고 다시 읽어야 한다.
- `clipMemories`는 그 관객이 읽은 클립 텍스트, 타인의 댓글, 자신이 쓴 댓글을 구분한다. 라이브 목격 저널과 별도이며 입장 전 방송을 직접 본 기억으로 바꾸지 않는다. 안정된 ID를 사용하므로 닉네임이 바뀌어도 자기 댓글을 기억한다. 예전 읽기 기록이 없는 댓글은 작성자 자신의 말만 기억하고, 주변 채팅·댓글·설명을 읽었다고 추정하지 않는다. 첫 새 읽기 이후에도 오래된 자기 댓글은 유지한다.
- 공개 클립 조회·목록·state/export에서는 내부 읽기 기록을 제외한다. 익명 후원은 공개 이름과 당시 포인트만 전달하며 저장소의 추가 내부 필드를 모델 입력으로 옮기지 않는다. 자기 말/타인 말, 가상 기획, 원문 발췌, 자동 STT 교정의 불확실성을 유지한다.
- 개인 회상은 최대 클립 2개, 각 원문 4개로 제한한다. 원문 본문은 각각 220자, 장면 요약은 240자이며 잘랐다는 표시와 출처를 함께 준다. 최근 읽은 스트리머 댓글 2개를 우선 확보해 정정·취소가 오래된 인용에 묻히지 않게 한다. 남은 칸과 클립 순서는 제한된 문자 어휘 일치와 최신 시각으로 고른다. 의미 검색이나 완전한 대화 이해를 보장하는 순위가 아니다.

원문 해시는 내용 버전 확인용이며 로컬 파일 소유자에 대한 암호적 보안 경계가 아니다. 공개 투영 필드/해시 형식을 바꾸는 후속 개발에서는 기존 읽기 기록의 이전 절차를 함께 검토해야 한다. 관객별 입력은 여전히 한 모델 요청에 함께 들어가므로 실행상 격리도 아니다.

## 검증과 수정 중 발견한 문제

`test/clip-memory.test.js`는 실제 HTTP, 인증 실패, 디스크 재시작, 개명, 관객별 입력, 삭제, JsonStore rename 실패, 모델 대기 중 삭제·추가, 대댓글 조상, 이전 버전 댓글, 원문 버전, 미래 시각, 익명/STT/가상 기획, 손상된 읽기 연결과 출력 크기를 검사한다. 첫 실행의 두 실패는 요청에 클라이언트 헤더가 없어 인증 전 403이 난 검사와 JSON에서 undefined 필드가 생략되는 비교였다. 인증 조건과 저장 표현을 올바르게 맞춘 뒤 제품 경로를 확인했다. 실패 원본은 `artifacts/clip-memory-tests.log`에 보존했다.

추가 회귀에서 **첫 읽기 기록을 만든 뒤 최근 창 밖의 예전 자기 댓글이 사라지는 문제**를 재현했다(`artifacts/clip-memory-legacy-before.log`). 자기 댓글의 원문 소유권과 새 읽기 창을 분리해 고쳤다. 캐시 도입 뒤에도 중첩 후원 정보 수정, 반환 객체 변경, 다른 클립 커밋이 잘못된 기억으로 이어지지 않는 검사를 추가했다. 최종 기능 검사는 12개이며 원본은 `artifacts/clip-memory-tests-optimized.log`다.

초기 실제 Astra 검사 `artifacts/clip-memory-astra-qRBKlV`와 예전 자기 댓글 보존 후 `artifacts/clip-memory-astra-rMvRcT`는 각각 여섯 흐름을 통과했다. 각 흐름은 실제 클립 댓글 생성 → 파일 저장 → 서버 재시작 → 실제 라이브 응답을 포함한다. 한 흐름에 정정 댓글 재읽기가 있어 실행마다 총 13개 모델 호출이다. 최종 캐시 코드의 결과는 아래에 별도로 기록한다. 이전 모델 결과를 수정된 코드의 최종 검증으로 제시하지 않는다.

## 용량과 반복 처리

합성 클립 100개, 각 채팅 25개·댓글 150개, 관객 한 명이 모든 댓글을 읽은 약 20.2 MB 프로필을 JSON으로 저장·복원해 조회했다. 첫 구현에서 한 번의 조회가 약 0.8~0.9초 걸렸고, CPU 프로파일에서 반복 정규화/정규식과 해시 계산이 큰 비중을 차지했다. 원본: `artifacts/clip-memory-recall.cpuprofile`, `artifacts/clip-memory-capacity-profile-result.json`. 프로파일러가 측정에 영향을 줄 수 있다.

원문 객체별 캐시는 공개 값이 모두 같을 때만 해시·정규화를 재사용한다. 중첩 교정/후원 필드를 비교하고 `updatedAt`만 믿지 않는다. 저장 후 전체 객체가 복사되더라도 같은 원문 버전의 캐시를 이전하며, 읽은 사람과 삭제 여부는 매번 다시 확인한다. WeakMap을 사용하므로 과거 전체 저장소를 강하게 붙잡지 않는다. 출력의 중첩 객체는 복사한다.

최종 캐시 구현의 `artifacts/clip-memory-capacity-verified.json`: 첫 조회 **572 ms**, 다음 네 번 **68~87 ms**, 다른 댓글 삭제 커밋 후 **84 ms**였다. 결과는 클립 2개·원문 8개·6,633 bytes였다. 첫 조회의 인덱스 생성 비용은 여전히 남아 있다. 단일 관객 합성 자료의 프로세스 시간이며 실사용 FPS, 여러 관객 전체 지연, 실제 저장 쓰기 시간이나 모델 지연 개선을 입증하지 않는다. 해당 벤치마크의 108 ms 변경 시간은 메모리 복사/캐시 이전이며 저장 어댑터가 비어 있어 디스크 쓰기 성능으로 사용하지 않는다.

## 남은 범위

- 클립 **댓글 자체**에는 “댓글로 보니…군요”와 불필요한 감상·웃음이 남을 수 있다. 라이브 기억 연결의 성공을 클립 말투 완성으로 일반화하지 않는다.
- 클립 유입으로 새로 태어난 관객, 읽기만 하고 댓글을 쓰지 않은 관객, 커뮤니티 일반 게시물까지의 경험 전달은 별도 경로다. 단지 origin에 clipId가 있다는 이유로 새 읽기 기억을 부여하지 않는다. 자율적인 읽기/댓글 빈도와 주제 복귀를 포함한 장기 평가는 남아 있다.
- 클립 읽기/댓글은 같은 저장 단위지만 기존 audience 친밀도·마지막 말 저장은 여전히 그 뒤의 별도 world 저장이다. 전체 저장소의 통합 트랜잭션 완료를 주장하지 않는다.
- 이 삭제 검사는 클립·클립 댓글의 원본 삭제다. 다른 저장소에 이미 인용된 문장이나 별도로 보존한 클립의 복제 채팅까지 모두 지우는 전역 삭제 계약은 별도 검토가 필요하다.
- 사용자 앱 재시작·패키지 교체·네이티브 장치/게임 시험은 이번 단계에서 수행하지 않는다. 이전 `2026-09-13T09-55-22-753Z` 패키지는 최신 회상·클립 기억 변경 이전 코드다.

## 최종 실제 모델·전체 검사

최종 소스에서 공식 CLI **gpt-6-astra / low**로 `artifacts/clip-memory-astra-fHAQuB/result.json`의 여섯 흐름을 다시 실행했다. 클립 댓글 7개 호출과 재시작 후 라이브 6개 호출, 총 **13개 실제 모델 호출**이다. 각 사례의 `calls.json`에 요청 입력과 출력, 각 단계 지연을 보존했다. 라이브 응답은 9.623~12.730초였다.

| 확인 내용 | 실제 라이브 답변 |
|---|---|
| 읽었던 별명과 간접 경험 | 야간열차요! 실시간으로 본 건 아니고, 클립 댓글에서 그렇게 정하신 걸 읽었어요. |
| 읽은 뒤 추가된 댓글 | 새 댓글의 암호는 몰라요. 제가 읽은 건 별명을 ‘야간열차’로 하신다는 댓글까지예요. |
| 읽지 않은 다른 관객 | 그 별명은 제가 모르겠어요. |
| 익명 후원자 | 클립에 남은 채팅에는 '익명의 관객'이라고만 나와서 누군지는 모르겠어요. |
| 삭제한 클립 | 그 별명은 기억이 안 나요. 뭐였죠? |
| 다시 읽은 정정 | 별빛철도요! 클립 댓글에서 그걸로 바꾸셨죠. |

제한된 문구 검사는 여섯 사례 모두 통과했고, 원문 전체도 읽었다. 13개 응답 모두 과거 클립을 새 포인트 보상 사건으로 만들지 않았다(`artifacts/clip-memory-model-review.json`). 이 검사와 내부 `factsPassed`가 일반적인 사실 정확도·자연스러움 합격 점수는 아니다. 특히 클립 댓글 생성에는 비슷한 “이름만으로 여행 느낌” 감상과 웃음이 반복됐다. 같은 한 명/소재의 독립 표본이며 장기 도배를 관찰한 것은 아니지만, 표현 다양성의 후속 평가 대상으로 남긴다.

기능 검사 **12개**, 전체 **412개 검사 및 TypeScript/Vite 빌드**가 통과했다. 최종 원본은 `artifacts/clip-memory-tests-optimized.log`, `artifacts/check-verified.log`다. 변경 전·중간 단계의 검사와 모델 결과도 보존했으며, 통합과 이전 후원 회귀 결과는 이어 기록한다.

기존 후원 회상 스크립트도 최종 코드로 실제 호출했다. `artifacts/donation-memory-astra-8AoVrX/result.json`의 **3사례 모두 통과**, 8.266~11.921초였다. 두 목격자 질문에는 실제 24P를 답하고, 신규 관객은 금액을 모른다고 했다. 과거 후원이나 일반 채팅의 지급 약속으로 새 보상을 만들지 않았다. 이번 최종 코드의 실제 호출은 이를 합쳐 16개다.
