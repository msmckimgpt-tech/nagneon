# Windows 저장 파일 교체

JSON 기록은 검증된 임시 파일을 끝까지 기록하고 fsync한 다음, rename으로 기본 파일을 교체한다. Windows에서 다른 프로세스가 삭제 공유를 허용하지 않는 읽기 핸들을 잠깐 유지하면 이 교체가 `EPERM`으로 실패할 수 있다.

`JsonStore`는 Windows의 최종 커밋 rename에서 발생한 `EPERM`에만 10ms, 20ms, 40ms를 기다린 뒤 재시도한다. 최초 시도를 포함해 최대 4회이며, 다른 오류나 Windows 이외의 플랫폼은 즉시 오류를 전달한다. 오류 종류가 도중에 달라지면 현재 오류를 전달하고, 한도를 소진하면 마지막 오류를 그대로 전달한다.

재시도는 이미 준비된 임시 파일의 교체에만 적용한다. 임시 기록·fsync·백업 회전·손상 원본 보존을 반복하지 않고 기본 파일을 먼저 삭제하거나 권한을 변경하지 않는다. 성공한 뒤에만 저장 캐시를 새 값으로 갱신한다. 실패하면 기존 임시 파일 정리 절차를 수행하고 오류를 전달한다. 기존 백업 실패 경고와 손상 파일 보존 실패 시 저장 중단 정책은 유지한다.

재시도 대기 합계는 최대 70ms다. 저장은 동기 작업이므로 이 대기 동안 서버 이벤트 처리가 잠시 멈춘다. 파일 시스템 호출 자체의 지연까지 포함한 전체 저장 시간의 상한은 보장하지 않는다. 계속 유지되는 잠금이나 권한 오류를 해결하는 기능은 아니다.

회귀 검사는 일시적·지속적 실패, 오류 종류 변경, 신규 파일, 백업 회전, 손상 원본 보존, 재시작 후 읽기를 확인한다. Windows 파일 핸들을 독립 프로세스로 열고 해제하는 별도 실행 검사는 실제 공유 충돌에서의 교체와 이전 데이터 보존을 확인한다. 통제된 재현은 발생 가능한 오류 종류의 증거이며, 다른 실행에서 발생했던 오류의 정확한 점유 프로세스를 확정하지 않는다.
