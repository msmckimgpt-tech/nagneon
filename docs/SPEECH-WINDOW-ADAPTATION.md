# 긴 음성 입력의 연산 길이 조절

기준 main `c9e74359be75236eb24ca4a0438635ca5cc45e7a`, worktree `G:/dev/ai/00_game_backseat-worktrees/speech-window-adaptation`, 브랜치 `codex/speech-window-adaptation`. 이전 배포 검증에서 9.4초 합성 발언의 전사에 약 10초가 걸렸다. 이 문서는 해당 인식 비용을 줄이는 변경과 실제 파일 비교를 기록한다.

## 원인과 변경

기존 worker는 6.5초까지 8초 encoder 입력을 사용하지만, 그보다 길면 즉시 30초 경로로 돌아갔다. 정상 렌더러는 `VOICE_MAX_MS=6000`으로 발화를 나누므로 모든 일반 발언에 10초가 걸린다는 뜻은 아니다. 지연된 브라우저 콜백이나 별도 긴 입력은 긴 경로로 들어갈 수 있다. 이 검증은 그 입력의 전사 비용이며 실제 물리 캡처 지연이나 관객 응답 시간을 측정한 것이 아니다.

고정된 [CTranslate2 4.8.2 encoder](https://github.com/OpenNMT/CTranslate2/blob/v4.8.2/src/layers/whisper.cc#L22-L55)는 최대 길이 이하의 입력을 허용한다. 설치된 [faster-whisper 1.2.1](https://github.com/SYSTRAN/faster-whisper/blob/v1.2.1/faster_whisper/transcribe.py)의 feature padding과 segment 경로도 읽었다. 제품은 이를 이용해 실제 샘플 수에 따라 8/12/16초 중 충분한 길이를 고른다.

| 음성 길이 | 첫 encoder 입력 | 보존 범위 |
|---|---:|---|
| 0초 초과~6.5초 | 8초 | 기존 짧은 발화 경로 |
| 6.5초 초과~10.5초 | 12초 | 발화 전체와 최소 1.5초 패딩 |
| 10.5초 초과~14.5초 | 16초 | 발화 전체와 최소 1.5초 패딩 |
| 14.5초 초과 또는 빈 입력 | 30초 | 기존 긴 입력/다중 segment 경로 |

파형을 자르거나 모델·한국어·CPU/int8·스레드4·beam3·VAD·타임스탬프를 바꾸지 않는다. 불확실한 첫 결과는 기존 30초 경로로 재처리한다. 모든 종료/예외에서 길이를 원복한다. `encoderWindowMs`는 첫 시도의 길이를 유지하고 `encoderPassesMs`에 첫 전사/재전사 시도에 설정한 길이 목록을 기록한다. 실제 encoder 호출 횟수나 실행 시간은 아니며, VAD가 무음을 거르면 encoder 자체가 실행되지 않을 수 있다. 이 진단 정보는 사용자 음성 자동 수집을 추가하지 않는다.

## 증거와 범위

모든 증거는 개발 worktree의 `artifacts/` 아래다. 사용자 앱·장치·게임·화면을 실행하거나 조작하지 않는다. 이전 검증 배포본에서 Python과 medium 모델 **2,351개 파일 / 1,796,366,838바이트**를 별도 worktree에 복사했으며 각 파일을 원래 매니페스트와 복사 전후 SHA-256으로 확인했다(`window-inputs.json`). 원본은 수정하지 않았다.

Windows Microsoft Heami Desktop을 파일 출력으로만 사용해 새로운 긴 발언 8개와 느린 속도 2개를 만들었다. 기존 합성 짧은 한국어15개와 9.4초 발언도 복사했다. Gaussian 15dB 잡음6개, 무음2개, 끝부분에만 발언이 있는 경계 입력3개를 더한 **37개 합성 입력**으로 확장했다. 정답·파형 해시·잡음 seed·파생 출처를 `window-corpus/expanded.json`에 남긴다. 실제 사용자 목소리나 게임 소음의 대표 표본은 아니다.

합성 helper의 첫 실행은 PowerShell 실행 정책으로 시작 전에 거절됐다(`corpus-synthesis.log`). 검토한 파일 출력 코드에 대해서만 자식 프로세스의 실행 정책을 지정해 실행했고 전역 정책은 바꾸지 않았다(`corpus-synthesis-final.log`). 입력이 만들어지기 전 실패였으며 부분 corpus를 덮어쓴 재시도가 아니다.

예비 비교 `window-probe.json`은 원본 worker와 prototype을 같은 medium 모델·동일 입력으로 실행했다. 4개 긴 입력을 두 번씩 번갈아 처리한 8쌍에서 문자 오류4/304가 같고, 중앙값은 6,048ms에서 2,708.5ms였다. '이따가/있다가' 표기 차이는 양쪽에 동일하게 남았다. 예비 prototype과 최종 제품 검증을 구분한다.

`test/speech-worker.test.py`는 9개가 통과했다(`worker-tests.log`). 실제 ndarray의 마지막 샘플까지 보존, 세 구간의 경계 한 샘플 차이와 패딩, 긴 입력 원래 경로, 낮은 확신 재시도, 재시도 예외 후 다음 요청, 무음, 선택적 음성 단서 실패, 오류 요청 ID를 검증한다. 이 Python 검사는 가짜 추론이며 실제 모델 결과는 아래 비교에서 별도로 확인한다.

## 최종 비교

`window-comparison.json` / `comparison.log`는 **37개 고유 입력, 56쌍, 실제 전사112회**의 결과다. 짧은 회귀 입력은 한 쌍씩, 긴 입력과 경계/무음은 순서를 바꿔 두 쌍씩 실행했다. 원본과 후보 모두 **23/1,296자 오류, 46/56건 전체 일치**였으며 입력별 문자 오류 증가 사례가 없었다. 이 숫자의 분모에는 반복 측정이 포함돼 있다. 불일치와 문자열 차이가 있는 모든 고유 사례를 직접 읽었고, '물약→무략/무량', '빨간→밝은', 일부 어미 오류가 양쪽에 똑같이 남아 있음을 확인했다. 문장부호·띄어쓰기만 달라진 사례도 따로 구분했다. 이 변경으로 그런 기존 오류를 해결했다고 보고하지 않는다.

속도 해석에서는 무음과 끝부분에 짧은 말만 있는 대조 입력을 제외했다. 연산 범위가 바뀌는 **긴 발화13개 ×2회 =26쌍**의 처리 시간 중앙값은 **6,148ms → 2,426ms**, 총 처리 시간은 **158,477ms → 66,660ms**였다. 기준 범위는 5,266~7,254ms, 후보는 2,041~4,336ms이며 이 26쌍의 fallback은 양쪽 모두0회다. 원본은 `window-analysis.json`에 있다. 같은 시점의 비교이며 이전 배포에서 측정한10초와 결합해 개선율을 계산하지 않았다. 실제 장치·게임 부하나 모든 억양에 일반화하지 않는다.

파생 무음2개는 환각 발언이 없었고, 10.5/14.5초 입력의 마지막에만 있는 '그렇습니다'도 보존했다. 14.5초보다 한 샘플 긴 입력은 기존30초 경로를 사용했다. 재시도 정책 자체는 Python9개 회귀로 확인하며, 실측에서 fallback이 없었다는 사실을 실제 불확실 음성 재시도 합격으로 대신하지 않는다.

## 배포와 통합

필수 **495개 Node 검사와 TypeScript/Vite 빌드**가 통과했다(`check-canonical.log`). 새 배포 폴더는 이 worktree의 `release/2026-09-13T14-46-24-910Z/app/BACKSEAT-win32-x64`, **2,451개 파일 / 3,130,142,882바이트 / 미서명**이다. 실제 배포 ASAR의 모듈과 동봉한 medium 작업자로 9.4초 발언이 12초 경로를 사용하는 것을 확인했다. 그 작업자를 전사 중 종료해 복구하고 짧은 한국어4개를 같은 세션에 전달했으며, 동시에 실행한 별도 YAMNet/small 인식기도 완료됐다. 시험 소유 작업자의 종료도 확인했다.

`window-delivered-Hpm42Q/result.json`, `delivered-canonical.log`, `window-final-build-result.json`이 실제 실행 원본이다. 그 보고서와 같은 ASAR에 대해 전체2,451개 파일 SHA-256, 현재 소스67개, fuses가 통과했다(`package-integrity-test.json`). 이번 변경은 음성 전처리/진단뿐이므로 Astra 호출은 추가하지 않았으며, 이전 배포의 모델 응답2회를 이번 새 배포에서 실행한 것처럼 합산하지 않는다.

서명·네이티브 설치·물리 마이크·실제 게임 중 체감·장기 채팅 품질·Steam 판매 조건은 별도의 남은 기준이다. 사용자 앱을 교체하거나 재시작하지 않았다. 이어서 요청된 2차 실사용 분석은 별도 작업 트리에서 원본 기록을 읽고 진행한다.

Windows checkout에서도 배포 소스 해시가 같도록 수정한 worker 하나를 LF로 정규화하고 `.gitattributes`에 해당 파일만 지정했다. 전후 Git canonical blob은 같으며 `worker-eol.json`에 바이트 해시를 남겼다. 정규화 후 Python9개, 필수495개/빌드, 새 배포 실제 인식기 복구와 전체 무결성 검사를 다시 통과했다. 처음 혼합 줄바꿈 배포의 `window-build-result.json`은 중간 검증으로 보존한다.
