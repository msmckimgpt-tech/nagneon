# 늦게 도착한 관객 핫클립의 영상 복구

2026-09-13, `codex/clip-buffer-recovery`, 기준 `a41678c5ddf36406c5f330821aafd5d4b5931efe`.
사용자 테스트 중단 정책을 유지한 코드·파일 기반 작업이다. 실제 사용자 화면·소리·대화를 시험 입력으로 사용하지 않았고, 사용자 앱을 조작하거나 재시작하지 않았다.

## 확인한 문제

기존 `useClipBuffer`는 독립된 15초 녹화 중 가장 최근에 끝난 구간 하나만 보관했다. 모델이 관객의 선택을 늦게 반환하면 관객이 본 시각의 영상은 이미 사라질 수 있었다. 하나의 `resolveTake`만 허용해 동시 요청 하나가 거절됐으며, 영상 전송 전에 `attachedClips`에 등록해 일시적인 전송 실패도 해당 클립을 다시 시도하지 않았다.

기준 커밋의 **실제 hook 소스**를 TypeScript로 변환하고 가상 시계·녹화 이벤트로 실행했다. 105초 후의 5초 시점 선택은 `null`이었고, 두 동시 선택 중 하나는 `이전 클립을 저장하고 있습니다.`로 거절됐다. `artifacts/clip-buffer-baseline-result.json`에 소스 SHA-256과 결과를 보존했다. 실제 방송 기록에서 이 문제가 발생했다는 주장이나 브라우저 녹화 검사는 아니다. 현재 관객 선택의 1분 간격 제한도 변경하지 않았다.

## 변경

- `src/clip-buffer.ts`: 완료된 독립 녹화를 종료 후 120초, 최대 10개·합산 24MiB로 보관한다. 공간이 부족하면 오래된 구간부터 버린다. 활성 녹화의 수신 바이트는 별도로 최대 20MiB이며 초과 시 캡처 복제본을 정리한다. 이는 Blob 데이터 한도이며 브라우저 인코더를 포함한 프로세스 전체 메모리 상한은 아니다.
- 선택한 `observedAt`을 포함하는 구간만 반환한다. 최신 장면으로 대신 채우지 않는다. 여러 관객은 동일한 완료 구간을 함께 기다릴 수 있다. 선택 시 녹화를 강제로 잘라내지 않고 정상 15초 구간이 끝날 때까지 받아 선택 이후 반응도 담는다. 구간 종료 응답은 추가 4초까지 기다리며, 중단·오류·초과 대기는 `null`로 해소한다.
- 종료 요청 시각과 종료 콜백 시각을 분리해 인코더를 다시 시작하는 틈을 녹화한 것으로 표시하지 않는다. 1초 미만·45초 초과 구간은 연결하지 않는다. 설정, 방송 세션, 화면·마이크·출력 소스가 바뀌면 이전 버퍼와 대기 작업을 정리한다.
- `src/clip-uploads.ts`: 세션별 큐가 영상을 하나씩 연결한다. 동일 클립의 상태 반복 통지는 중복 전송하지 않고, 삭제되거나 이미 저장된 대기 항목을 제거한다. 동일 Blob을 유지한 채 1초·3초 후 최대 2회 재시도하며, 먼저 서버에서 이미 저장됐는지 확인한다. 마지막 실패 후에도 한 번 확인해 저장 성공 응답 유실을 복구한다. 개별 전송은 본문 수신까지 10초 제한이며 최종 실패 알림은 한 번이다.
- 방송·화면·마이크·소리 중단과 저장 설정 해제는 진행 중 요청을 취소한다. 녹화 완료 뒤와 각 재시도 전에도 세션·권한을 확인한다. 전송이 서버에 이미 도착해 저장된 파일까지 소급 삭제하지는 않는다.
- 핫클립 화면은 임시 버퍼와 구간 완료 대기를 설명한다. 마이크만 포함할 때도 맞도록 `공유 소리 포함` 표시를 `소리 포함`으로 조정했다. 생성 권한은 계속 관객에게 있다.

컨테이너는 각 녹화의 모든 청크를 하나로 합친다. 독립 녹화 여러 개를 임의로 이어 붙이지 않는다. 개별 timeslice 청크는 재생 가능성이 보장되지 않고 완료 녹화 전체가 재생 단위라는 [W3C MediaStream Recording 규정](https://w3c.github.io/mediacapture-record/#data-handling)을 따른다. 브라우저의 이벤트 지연으로 실제 녹화 길이는 타이머와 차이가 날 수 있다.

## 검증

- `npm ci`: worktree 자체 의존성 설치, 취약점 보고 0. 최종 `npm run check`는 323개 검사(새 회귀 검사 22개)와 TypeScript/Vite 빌드를 통과했다. 원본: `artifacts/clip-check-final.log`.
- `test/clip-buffer.test.js`, `test/clip-uploads.test.js`: 지연 선택, 동일 구간 동시 요청, 마지막 데이터 이벤트, 재시작 틈, 만료·미래 시각, 바이트 한도, 오류·중단·종료 콜백 유실, 두 번째 인코더 생성 실패, 중복 상태 통지, 동일 바이트 재시도, 성공 응답 유실, 유한 재시도, 동의 철회, 전송 취소·타임아웃, 세션 구분, 삭제·이미 저장된 대기 항목을 검증한다. MediaRecorder와 시간은 주입한 시험 대역이며 장치 시험이 아니다.
- `scripts/verify-clip-transfer.mjs artifacts/clip-synthetic.webm artifacts/clip-transfer-final`: 가상 녹화 이벤트로 **실제 합성 WebM 파일**을 production buffer → upload queue → 별도 실제 HTTP 서버 → 디스크에 전달했다. 선택 시각은 100초 전이며 이후 6구간과 다른 파일 바이트를 사용해 최신 영상으로 바꿔치기되지 않는지도 확인했다.
- 첫 POST의 서버 저장과 성공 응답 수신 후 클라이언트에 전송 오류를 주입했다. `POST, GET`만 발생했고 추가 업로드 없이 저장을 확인했다. 내려받은 163,888바이트의 SHA-256은 원본과 같은 `aa896dc3cf81a4cb00065d98a7809a481ee4d2fc287021bf7c54ee88491399dc`였다. HTTP 206 범위 요청, 별도 서버 종료·재시작 후 메타데이터와 영상 재조회도 통과했다.
- 영상 저장 허용 해제, 관객 클립 선택 해제, 다른 세션, 관객이 본 시각 밖의 영상은 실제 HTTP에서 각각 409로 거절됐고 추가 미디어 파일이 생기지 않았다.
- 저장 파일을 PyAV로 복호화해 75개 영상 프레임(5fps·15초), 첫/마지막 색상, 단일 영상·음성 트랙을 확인했다. 기존 `verify-clip-sound.py`로 440Hz와 880Hz 두 합성 소리를 확인했다. 마이크·loopback 캡처나 실제 게임 영상의 재생 검증을 대신하지 않는다.

원본은 이 worktree의 `artifacts/clip-*.log`, `clip-transfer-first/`, `clip-transfer-final/`, `clip-video-decode.json`, `make-clip-fixture.py`, `verify-clip-frames.py`, 기준 소스/재현 스크립트다. 사용자 자료는 포함하지 않는다. 전체 검사·통합 결과와 증거 목록은 아래 통합 기록을 따른다.

## 남은 수용 검사

15초 구간 경계에 걸친 긴 명장면을 앞뒤 녹화와 합치는 편집 기능은 구현하지 않았다. 소스 변경·동의 해제로 버퍼가 비워졌거나 메모리/시간 한도를 지난 장면에는 영상 대신 기존 장면 기록이 남는다. 화면을 연결하지 않은 Just Chatting의 대화 기록은 유지되지만 별도 음성 전용 핫클립 파일은 이번 변경 범위가 아니다.

실제 Electron MediaRecorder의 구간 경계·부하·장시간 사용, 사용자 앱에서 화면·마이크·출력 소리 변경과 영상 재생은 미검증이다. Computer Use 중단이 끝나도 자동으로 재개하지 않는다. 현재 실행 중인 사용자 앱이나 이전 배포 폴더를 덮어쓰지 않았다. Steam 판매 준비 완료로 해석하지 않는다.
