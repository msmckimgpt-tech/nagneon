# 핫클립의 녹화 맥락

관객의 선택 시각이 15초 녹화 조각의 끝에 가까우면 뒤 반응이 빠지고, 시작에 가까우면 앞 과정이 빠졌다. 이제 서로 겹치는 **독립적인 녹화본** 중 요청한 맥락을 가장 많이 포함하는 것을 선택한다. 서로 다른 WebM 파일의 바이트를 이어붙이지 않는다.

## 선택 범위

- 관객이 실제로 들은 발화·시스템 소리의 캡처 구간이 있으면 그 시작과 끝에 앞 8초·뒤 6초를 붙인다. 캡처 구간이 30초보다 길거나 유효하지 않으면 선택 시점 주변으로 돌아간다.
- 화면 선택처럼 사건의 시작·끝을 확인할 수 없으면 선택 시점 앞 8초·뒤 6초를 기본 여유로 사용한다. 이 값은 사건 전체를 의미적으로 인식했다는 뜻이 아니다. 새로운 모델 호출이나 영상 분석을 추가하지 않는다.
- 방송 시작보다 앞선 요청은 잘라낸다. 이전 방송·미래 시각의 캡처는 거부한다. 늦게 도착한 선택도 원래 관측 시각을 사용한다.
- 같은 방송·게임·미디어 종류에서 아직 저장되지 않은 후보들의 요청 범위가 겹치고 합친 길이가 45초 이하면 하나로 합친다. 최초 제목·선택 시각·목격자는 유지한다. 이미 저장된 클립은 수정하지 않는다.
- 후보가 대기 중 확장되면 업로드는 최신 범위를 기다린다. 시작 시각은 녹화본의 실제 시작을 유지하므로 요청보다 앞선 영상이 조금 더 포함될 수 있다. 완성된 녹화본을 다시 편집하거나 트리밍하지 않는다.

## 경계와 자원 상한

| 항목 | 동작 |
| --- | --- |
| 녹화 | 기본 30초 녹화를 15초 간격으로 시작. 요청이 있으면 끝을 조정 |
| 동시 인코더 | 소스별 최대 2개. 영상·시스템 소리와 분리 마이크가 있으면 총 최대 4개 |
| 길이 | 실제 캡처 1~45초. 최대 요청은 타이머 지연을 위해 44.5초에서 중지 예약 |
| 미디어 크기 | 녹화본당 20MiB, 소스별 완성·진행 중 Blob 합계 24MiB |
| 보관 | 종료 후 최대 120초, 최대 10개. 바이트 상한에 먼저 도달하면 더 일찍 제거 |
| 대기·업로드 | 소스별 대기 최대 100개, 업로드는 기존의 한 번에 한 개·제한된 재시도 유지 |
| 녹화 중지 | 종료 콜백 4초 감시. 실패 시 버퍼를 해제하고 장면·대화 기록은 보존 |

24MiB는 녹화 Blob의 크기 제한이다. 브라우저·네이티브 인코더·디코더·GPU 프레임의 전체 메모리 상한이 아니다. 지나친 스케줄러 지연으로 실제 캡처가 45초를 넘으면 저장하지 않는다.

시작 직후, 버퍼 제거, 늦은 모델 응답, 중지 콜백 지연 등으로 앞뒤 맥락을 모두 확보할 수 없으면 원래 선택 시각을 포함하는 가용 녹화본을 사용한다. 가용 녹화본 자체가 없으면 사진·대화 기록만 유지한다. 미디어 저장 시 `recordingContext.truncatedStart`와 `truncatedEnd`에 부족한 구간을 기록한다. 현재 화면에 이 필드를 별도 표시하는 UI는 추가하지 않았다.

소스 변경·동의 철회·방송 중지·재시작은 대기 중 녹화를 취소한다. 이전 버퍼의 결과는 새 소스·세션에 연결하지 않는다. 공유 중인 원본 화면·마이크 트랙은 버퍼 정리에서 종료하지 않는다. 저장 형식은 선택적 메타데이터를 추가하며 기존 클립·설정·프로필을 재가공하지 않는다.

## 합성 검증과 비용

`scripts/verify-clip-context.cjs`는 숨김 Electron에서 생성한 캔버스·톤만 사용한다. 앱 본체를 함께 마운트하지 않는 JSON 문서에서 실제 인코더, HTTP 업로드·검사기, 영상·음성 재생, 병합, 소스 변경·중단·재시작·취소와 저장 후 서버 재시작을 검증한다. `scripts/verify-clip-context-frames.py`는 생성된 영상의 준비·핵심·여운 색상 프레임을 별도로 디코딩한다. 개인 기록·물리 장치·모델 호출은 사용하지 않는다.

실제 320×180/10fps 및 1280×720/30fps 합성 녹화에서 15초 경계 선택과 확장 후 약 28.1초의 독립 영상·분리 마이크 저장 및 재생을 확인했다. 시작 직후 음성은 앞 구간 부족을 기록했다. 실제 음성 인코더의 약 1.0초와 44.5초 캡처도 디코딩됐다. 프레임 검사에서는 선택 전 준비·핵심·선택 후 여운이 모두 남았다.

동일한 합성 화면·분리 마이크를 기존 단일 인코더 버퍼와 겹침 버퍼에서 순차 실행하고, 각 구간에서 Electron `app.getAppMetrics()`를 1초 간격으로 6회 읽었다. 다음은 한 PC에서 한 번 실행한 관측이다.

| 조건 | 기존 → 겹침 |
| --- | --- |
| 320×180/10fps 렌더러 CPU 원시 수치 평균 | 0.51 → 0.81 |
| 320×180/10fps 렌더러 working set 평균 | 107.9 → 115.3MiB |
| 1280×720/30fps 렌더러 CPU 원시 수치 평균 | 3.54 → 9.65 |
| 1280×720/30fps 렌더러 working set 평균 | 244.1 → 273.7MiB |
| 1280×720/30fps 렌더러 private memory 관측 최대 | 183.1 → 224.3MiB |
| 1280×720/30fps GPU 프로세스 CPU 원시 수치 평균 | 1.17 → 1.06 |

CPU는 Electron의 `percentCPUUsage`를 그대로 기록한 값이며 GPU 프로세스의 CPU 수치는 GPU 사용률이 아니다. 전체 시스템·게임 성능, 1080p/4K, 60fps, 장시간 녹화나 다른 장치의 성능을 보증하지 않는다. 추가 인코더의 CPU 비용이 확인됐으므로 실제 게임 환경의 여유를 통합·설치 전 확인해야 한다. 비용을 줄이려면 향후 단일 인코더와 제한된 서버 리먹싱을 비교할 수 있지만 이번 구현에 새 미디어 편집 경로나 의존성을 도입하지 않았다.

버퍼 합성 회귀는 경계·가변 끝 시각·병합 대기·최소/최대 길이·만료·실제 캡처 공백·진행 중/완성 Blob 상한·고장·취소·세션 분리를 다룬다. 서버 회귀는 캡처 기반/fallback 범위, 저장 전 병합, 기존 기록 보존, 목격자 보존 및 저장 실패 롤백을 다룬다. 전체 필수 검사와 관련 회귀가 통과했으며 설치·실사용 게임 검증은 별도 단계다.
