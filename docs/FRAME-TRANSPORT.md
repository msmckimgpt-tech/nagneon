# 화면 요청의 바이너리 전송

네이티브 base64 변환을 지원하는 렌더러는 `/api/react`의 이미지 요청을 `application/vnd.nagneon.frame-v1`로 보낸다. 이미지가 없거나 해당 변환을 지원하지 않으면 기존 JSON 경로를 사용한다. 서버 오류 후 자동 재전송하지 않으므로 같은 관측을 두 번 처리하지 않는다.

형식은 `NGF1` 4바이트, big-endian 메타데이터 길이 4바이트, UTF-8 JSON, 순서대로 연결한 이미지 바이트다. 이미지 자리에 MIME 종류와 바이트 길이를 기록한다. 서버는 64KiB 메타데이터·3MiB 요청 제한, 프레임 수·이미지 길이·정확한 데이터 경계·UTF-8을 확인한다. 이미지 복원 후 기존 `Frame` 검증을 그대로 거친다. 압축을 푼 뒤의 JSON 크기도 기존 3MiB 한도를 유지한다.

프로세스 인증·요청 출처·앱 전용 헤더 검사는 본문 해석보다 먼저 수행한다. 사용자 파일 경로나 외부 URL은 받지 않는다. 방송·화면 ID, 촬영 시각, 같은 화면의 관측 구간은 바꾸지 않는다. 이후 취소·목격·모델 경로는 기존과 같다. 현재 서버는 호환성을 위해 data URL로 복원하므로 base64를 전체 처리 경로에서 제거한 것은 아니다.

## 검증과 범위

MCKIM / Electron 44.3.0의 숨겨진 창에서 결정적 합성 JPEG를 사용했다. 실제 renderer API와 인증된 HTTP 경로로 84개 요청을 보내 이미지 문자열과 방송·화면 ID·촬영 시각의 일치를 확인했다. Studio의 반응 부분만 모의 처리했으며 화면 장치·마이크·모델은 사용하지 않았다. 조건당 4회 준비 후 10회씩 JSON/바이너리 순서를 번갈아 측정했다.

| 이미지 수 | JSON → 바이너리 바이트 | HTTP 왕복 중앙값(ms) JSON → 바이너리 |
|---|---:|---:|
| 1 | 305,617 → 229,268 | 8.0 → 9.1 |
| 4 | 1,222,099 → 916,679 | 22.5 → 19.6 |
| 8 | 2,444,075 → 1,833,227 | 38.7 → 38.5 |

전송 본문은 약 25% 줄었다. 왕복 시간의 일관된 개선, 실방송 FPS나 모델 응답 속도 개선은 입증하지 않았다. 한 장에서는 오히려 소폭 늘었다. 일반 JavaScript `atob` 반복 변환은 별도 합성 측정에서 느렸으므로 지원하지 않는 환경은 JSON으로 유지한다.

`test/frame-wire.test.js`는 양식·길이·잘림·추가 데이터·인증·기존 JSON 호환·프레임 순서 거부를 검사한다. `scripts/verify-frame-wire.cjs`는 실제 Electron/HTTP 경로와 바이트 보존을 확인하며 Windows CI에도 포함한다. 원본은 `binary-frame-transport-20260923/artifacts/frame-wire-EouKe6/result.json`과 `native-wire.log`다. 이는 격리 실행 검증이며 배포 패키지·실제 방송 수용을 대신하지 않는다.
